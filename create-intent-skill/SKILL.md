# create-intent-skill

参照先をいくつも混ぜると、スキルの筋がぶれる。このスキルでは、先に「何を解決したいか」を決める。参照先のルールは、その解決に最短で役立つものだけを採る。

出力は、対象のプロジェクトのスキルの置き場所（無ければ `.claude/skills/<名前>/`）に置く3つのファイル。

- `SKILL.md`
- `policy.md`：方針
- `decisions.md`：ルールの採否と出典、形の判断、検証の仕方

手元の道具の使い方は、同じフォルダの `local.md` にある。ファイルが無ければ、その部分は飛ばす。

## 1. 方針を下書きして、人に確かめる

1. 読む：リポジトリの決まり（CLAUDE.md や AGENTS.md、CONTRIBUTING など）、最近マージされたプルリクエストとレビューのコメント、手元にあればプロジェクトの知識カード。
2. まず要求そのものを疑う。既存のスキル、メモリの1行、lint のどれかで済むなら、それを提案して止まる。
3. `policy.md` を下書きする。
   - 解決したいこと：本質的なところまで書く。1〜3個、それぞれ1文。
   - 非目標
   - 譲る順：方針どうしがぶつかったとき、先に譲るもの → 最後まで譲らないもの。
   - 各項目に根拠（ファイルのパスかプルリクエストの番号）を付ける。根拠が無い項目には「推測」と書く。
4. 人に見せる。直してもらうか、OK をもらう。

完了の条件：人が OK した `policy.md` があり、すべての項目に根拠か「推測」が付いている。

## 2. 参照先を3〜5件に絞る

1. [llms.txt](https://agent-taxonomy.kawaida-dev.com/llms.txt) の Bottlenecks か Jobs から、JOB の `.md` を開く。比較の表で候補を選び、エントリの `.md` を読む。
2. 解決したいことに直接役立つルールを持つものを選ぶ。似たものは1件にまとめる。
3. 上流の原文を読む。エントリの `.md` の source は既定のブランチを指すので、読む前にその時点の commit の SHA を取得し（例：`gh api repos/<owner>/<repo>/commits/<ブランチ> --jq .sha`）、SHA を固定した URL で読む。

完了の条件：`decisions.md` に、3〜5件の参照先が並んでいる。それぞれに、読んだファイルの URL（commit 付き）と、選んだ理由の1文がある。選ばなかった近いエントリと、選ばなかった理由も書いてある。

## 3. ルールごとに採否を決める

参照先からルールの候補を取り出し、次の順に当てる。

1. 解決したいことに役立たないものは、捨てる。
2. モデルが言われなくても自然にやることは、捨てる。
3. ほかの候補と同じ主張なら、1つにまとめる。
4. 残ったものをプロジェクトに合わせて簡単にする（直して採る）。

候補どうしがぶつかったら、譲る順で決め、どちらに決めたかを書く。

要旨は自分の言葉で、主張だけを書く。原文は写さず、訳さない。

`decisions.md` の表の形：`ID | 要旨 | 判定 | 理由（policy の項目）`。出典は参照先の表の ID で指す。

完了の条件：すべての候補に、判定と、理由になった policy の項目がある。

## 4. 形を決める

採ったルールの置き場所は、[Principles の「Writing a skill」](https://agent-taxonomy.kawaida-dev.com/principles/#authoring)の手順を上から当てて決める。

- 機械で判定できるもの：仕組みにする候補として書くだけにする。作るのは、使ってみて同じ誤りが2回起きてから。消せるものを消す前には、仕組みにしない。
- 起動のされ方：人が名前で呼ぶだけのスキルなら、`disable-model-invocation: true` にし、description は人向けの1行にする。

完了の条件：`decisions.md` の「形」の節に、手順ごとに当てた結果がある。

## 5. プロジェクトに合わせて書く

- 冒頭の1〜2文に、解決したいことを書く。
- 各手順の終わりに、完了の条件を置く。
- 本文には指示だけを書く。理由は `decisions.md` に置く。理由が無いと誤読されるルールにだけ、一言添える。
- 用語、コマンド、パスは、そのリポジトリのものを使う。設定ファイルやコマンドの出力から1回で分かることは書かない。
- 最初は、解決したいことに要る手順だけを入れる。
- 書いたら、次を検査する。
  - frontmatter に `name` と `description` がある。
  - 参照するファイルとリンクが実在する。

完了の条件：検査が通り、本文のどの手順も、解決したいことのどれかに結び付いている。

## 6. どう検証するかを書く

`decisions.md` の最後に、使いながら何を見て、いつ見直すかを1文で書く。例：その作業のプルリクエストで、手戻りのコミットとレビューの往復の回数を見る。テストケースは必須にしない。

スキルを直すのは、同じ失敗が2回起きてから。作業の途中では直さず、別のプルリクエストにする。

完了の条件：検証の仕方の1文が、見る値と、見直す時期を含んでいる。

## 返答

次の5つを返す。

- 解決したいこと
- 参照先（件数と名前）
- 判定ごとのルールの件数
- 形の判断の要点
- 検証の仕方の1文
