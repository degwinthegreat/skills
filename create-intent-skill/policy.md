# create-intent-skill の方針

create-intent-skill（agent-taxonomy の参照先から、意思に沿ってプロジェクト用のスキルを作るスキル）を設計するときの方針。ルールの採否（[decisions.md](decisions.md)）は、ここの項目番号で理由を書く。

- 決めた人と日付：持ち主（2026-11-11）。P1〜P6 は持ち主が決めた。非目標と譲る順は、エージェントが下書きし、持ち主が OK（2026-11-11）。

## 解決したいこと

agent-taxonomy の参照先をいくつも並べてスキルを書くと、ルールが混ざって筋がぶれる。そこで、何を解決したいのかを先に決め、その解決に必要なルールだけを参照先から採って、プロジェクト用のスキルを作れるようにする。

## 方針

- **P1. 意思を持って設計する（最優先）。** 何を解決したいのかを、本質的なところまで先に書く。意思は1つでなくてよい。参照先のルールは、その解決に最短で役立つかどうかで採るか捨てるかを決める。
- **P2. 追加するより削る。** モデルの能力を邪魔しない。モデルの考え方に合う、最小限の道具と指示だけを渡す。モデルが言われなくても自然にやることは、参照先にあっても捨てる。
- **P3. 段階の順番を守る。** 次の順で進める。
  1. 要求そのものを疑う
  2. 要らない手順やルールを消す
  3. 残ったものを簡単にする
  4. 回す速さを上げる
  5. 最後に自動化する（仕組みにする）

  消す前に仕組みにしない。

- **P4. 小さく始めて、使いながら育てる。** 最初から全部入りにしない。追加するのは、同じ失敗が実際に繰り返されてから。
- **P5. 方針は下書きして確認する。** 解決したいこと・非目標・譲る順は、エージェントが下書きする。材料は、リポジトリの決まり、過去のプルリクエスト、手元にあればプロジェクトの知識カード。人は直すか OK するだけ。
- **P6. 使いながら検証する。** テストケースは必須にしない。手戻りやレビューの往復の回数を使いながら見る。どう検証するかの1文を、スキルの出力に必ず入れる。

## 非目標

- 参照先の比較や一覧を作ること。それはサイトの仕事なので、スキルは結論だけを持つ。
- 評価のループ（スキルあり・なしで並べて実行し、採点する仕組み）を組むこと。P6 で使いながら検証する。
- 参照先の文を訳したり、並べ替えたりして持ち込むこと。作者の文は写さない。
- どのハーネスでもそのまま動くこと。対象は、手元で使うハーネスとプロジェクト。

## 譲る順

方針どうしがぶつかったら、上から先に譲る。

1. 網羅性（参照先の良いところを全部入れること）
2. 参照先への忠実さ（参照先の流儀に合わせること）
3. 汎用性（ほかのプロジェクトにも持ち運べること）
4. 手順の少なさ（P2・P4）
5. 意思（P1）。最後まで譲らない

作者の文を写さないことと、推測で値を埋めないことは、譲る対象にしない（どの場合も守る）。

## /principles の原則の群との対応

[/principles](https://agent-taxonomy.kawaida-dev.com/principles/) の群と、この方針の対応。

- **Subtract before you add**（subtract-first）：P2 と、P3 の「消す」「簡単にする」。この群には pstack の laziness-protocol（差分を最小にする）も入っている。
- **Encode repeated lessons in structure**（encode-in-structure）：P3 の最後の段階。P3 はこれに順番を加える。消せるものを消したあとで、それでも繰り返す誤りだけを仕組みにする。
- **The context window is a budget**（context-budget）：P2 の「最小限の指示」。常に読み込まれる description を短くし、手で呼ぶスキルにする判断に使う。
- P3 の「要求そのものを疑う」に当たる群は無い。近いのは pstack の attack-the-premise（/principles では借用として扱い、群には数えていない）。ただし、attack-the-premise が疑うのは、失敗した修正どうしに共通する前提で、要求そのものではない。
- P4 に当たる群は無い。根拠は decisions.md の PS1。
