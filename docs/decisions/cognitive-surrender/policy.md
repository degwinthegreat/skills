# cognitive-surrender の方針

cognitive-surrender（人が出力を明け渡していた所を見つけるスキル）を設計するときの方針。ルールの採否（decisions.md）は、ここの項目番号で理由を書く。

用語は、Addy Osmani の記事「Cognitive Surrender」（decisions.md の参照先）の区別に揃える。

- **任せる**（offloading）：やり方は渡すが、何を作るかと、良し悪しの判断は持ち続ける。
- **明け渡す**（surrender）：自分の答えを持たないまま、出力をそのまま自分のものにする。
- **候補**：任せたのか明け渡したのかを確かめる候補。人が確かめずに通したもの、見るのをやめたもの、手で避けているもの。

## 方針

- **P1. 週に一問だけ聞く。** 問いは、今週、確かめずに通したもの、見るのをやめたもの、手で避けているもの。答えが候補になる。答えが無くてもよい。根拠：エージェントの提案1に持ち主が賛成（2026-11-11）。
- **P2. 速く通したものを抜き取り、任せただけか、明け渡していたかを見分ける。**
  - 週に2〜3件を選ぶ。選ぶ材料は次の2つ。
    - 長い報告にすぐマージを返したもの、推奨のとおりに通したもの
    - 記事が挙げる明け渡しの兆し（大きな差分を流し読みで通す、根本原因を知らずに直す、自信のある説明で設計を受け入れる、など）
  - 選んだものを、文脈を引き継がない別のエージェントに確かめさせる。見るのは、人が何を作るかと良し悪しの判断を持っていたか。
  - 問題が残っていれば、明け渡していた所として示す。
  - 根拠：エージェントの提案2に持ち主が賛成、見分けの意味と兆しの扱いは持ち主（2026-11-11）。
- **P3. 任せた度合いの数は、記録の道具がある環境でだけ使う。**
  - 数は、推奨のまま通した割合、承認までの時間と報告の大きさ。使い方は local.md に書く。根拠：エージェントの提案3に持ち主が賛成（2026-11-11）。
  - 数（時間、長さ、割合）は、道具の出力か、走らせたコマンドの出力だけを使う。モデルが自分で記録から数えたり、写したりした数は使わない。P2 で選んだ理由に数を書くときも同じ。根拠：create-intent-skill/SKILL.md の手順1の2。持ち主が OK（2026-11-11）。「走らせたコマンドの出力」を足して SKILL.md の手順2の6と揃えることは、持ち主が OK（2026-11-12）。
- **P4. 本体は、どの環境にもある材料だけで動く。** 材料は、Claude Code のセッションの記録（`~/.claude/projects` の jsonl）、git、プルリクエストの履歴。手元の道具の使い方は、create-intent-skill と同じく local.md で足す。道具の名前は公開のファイルに書かない。根拠：持ち主 2026-11-11（持ち運べる形の条件）、create-intent-skill/SKILL.md の冒頭と README の「local.md（任意）」。
- **P5. 見つけたものは直さず、渡す。**
  - スキルが原因なら improve-intent-skill に渡す。作業の進め方を直すなら retro に渡す。根拠：持ち主 2026-11-11（境界の条件）。分け方は持ち主が OK（2026-11-11）。
  - 記事が挙げる対策は、このスキルでは行わず、渡し先に添える。
    - 人の進め方の対策（先に自分の答えを書く、モデルに自分の答えへ反論させる、疲れたら作らせるのを止める、説明できない判断の理由を組み直す）は retro に渡す。
    - スキルや作業の仕組みの対策（終わりの条件に証拠を求める、差分を小さく保つ、マージの前に確かめの段を置く）は、スキルが原因なら improve-intent-skill、そうでなければ retro に渡す。
    - 対策の判定は下書き（持ち主の確認待ち）。
- **P6. 小さく始める。** 最初は P1 と P2 だけを入れる。足すのは、使って同じ失敗が2回起きてから。根拠：create-intent-skill/policy.md の P4。持ち主が OK（2026-11-11）。

## 非目標

- 履歴に残ったつまずき（手戻り、レビューの往復、エラー）から学ぶこと。それは retro の仕事。このスキルは、履歴に残らない候補を見る。根拠：持ち主 2026-11-11（境界の条件）。
- スキルを直すこと、見つけたものを直すこと。スキルの直しは improve-intent-skill、ほかは retro に渡す（P5）。根拠：持ち主 2026-11-11（境界の条件）。
- 任せること自体を減らすこと、人に全部を確かめ直させること。任せるのは多くの場合正しい。見るのは、候補が明け渡しになっていないかだけ。根拠：記事の区別と同じ。持ち主 2026-11-11。
- 長いアンケートを取ること。問いは週に一つ（P1）。答える手間が増えると、人は答えなくなる。根拠：エージェントの提案1に持ち主が賛成（2026-11-11）。理由の文は持ち主が OK（2026-11-11）。
- 評価のループ（スキルあり・なしで並べて実行し、採点する仕組み）を組むこと。P2 の確かめは、選んだものを1件ずつ見分けるだけで、採点しない。根拠：create-intent-skill/policy.md の非目標（同じ線引き）。持ち主が OK（2026-11-11）。
- 人の考え方や技能を鍛えること。たとえば、モデルと協力する考え方に変えること、AI を使わずに書く時間を持つこと。これらはスキルの出力では変えられないので、渡しもしない。下書き（持ち主の確認待ち）。

## 譲る順

方針どうしがぶつかったら、上から先に譲る。持ち主が OK（2026-11-11）。

1. 網羅性（候補を全部見つけること）。週に一問と2〜3件の抜き取りで足りる。
2. 数による裏付け（P3）。道具が無い環境では飛ばす。
3. 人の手間の少なさ（問いを一つ、抜き取りを2〜3件に抑えること）。
4. 持ち運べること（P4）。
5. 意思（履歴に残らない明け渡しを見つけること）。最後まで譲らない。

次の4つは譲る対象にしない（どの場合も守る）。

- 公開のファイルに手元の道具の名前を書かない。
- 見つけたものをこのスキルで直さない。
- 数を推測で埋めない。
- 参照先の文を写さない。
