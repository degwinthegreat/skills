# create-frontier-team の図（canvas.html）の設計書

- 状態：下書き（2026-11-15）。場面の問い、成功の定義、棚卸しの表の判定は、エージェントが推奨で埋めたもの。持ち主と一緒に決める（決める所は「未決の問い」）。
- 対象：[create-frontier-team/canvas.html](../../create-frontier-team/canvas.html)。根拠のコードは [3e4fc5c の版（#25 のあと）](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html) で指す（行番号もこの版のもの）。
- 書き方：intent-spec（このリポジトリの、仕様書を書くスキル）の「参考に作る」の入口（すでにあるものを材料にし、機能ごとに採る・採らない・変えるを決める）で書いた。参考にするのは今の図で、棚卸しの表が「採る・採らない・変える」の表を兼ねる。
- 例：架空のチーム「そらまめ」の仕様書（4 つの段階、段階つきの gap と検査、マージのあとの検査つき。#25 の例と同じ）を [frontier-canvas/soramame.json](frontier-canvas/soramame.json) に置いた。画面はこれを 3e4fc5c の図に埋め込み、1440×900 で撮った。

## 目的

図は #21〜#25 で、出てきた不満（線が複雑、文章が多い、関門の中が見えない、段階、人の作業の「スキル無し」）を 1 つずつ直してきた。そのたびにトグル、印、タブ、窓が増え、「図はだいぶ良くなったが、ナビゲーションが複雑になってきた」（持ち主、2026-11-15）。

原因は、図が「誰が・どの場面で・何を答えるために開くか」を決めないまま、全部を 1 枚でこなそうとしてきたこと。成功の定義も無い。create-frontier-team は「設計書から作る」と言いながら、図そのものには設計書が無かった。

この設計書は、図を開く場面ごとに答えたい問いと成功の定義を決め、今の図に出ている情報を場面に照らして棚卸しし、ナビゲーションの形を選ぶための材料にする。進め方は 3 つの段に分ける：(1) この設計書を持ち主と決める（この PR）。(2) 決まった成功の定義で今の図を評価する（[次の段の段取り](#次の段の段取り)。図は直さない）。(3) 評価の結果を受けて図を直す（その次の PR）。

## 図を開く場面

持ち主が確かめた 3 つの場面（2026-11-15）。問いと成功の定義は下書き。

成功の定義は 2 段で書く。「人の基準」は持ち主が見て判定する。「試しの基準」は、人物像を決めたエージェントに図だけを渡して判定する（[次の段の段取り](#次の段の段取り)）。エージェントは秒を測れないので、試しの基準は「操作の回数」と「答えが仕様書と合うか」で書く。操作の数え方：クリックとキーを押すのは 1 回ずつ、一続きのスクロール・ドラッグ・ズームは 1 回、カーソルを当てるだけは数えない。「開いたとき」は、その場面の見方を選んだ状態から数える（既定の見方が違えば、切り替えの 1 回を足す。既定は未決の問い 1）。

### 場面 a：流れの全体を初めて掴む

- 見る人：チームに新しく入った人。久しぶりに見る本人。仕様書の JSON も設計書も読んでいない。
- 答えたい問い
  - a1：流れは何段で、どこから始まり、どこで終わるか。
  - a2：誰（人・エージェント・自動）がどこを動かし、人はどこで判断するか。
  - a3：どこで判定し、通らなければどこへ戻すか（関門と戻り道）。
- 成功の定義
  - 人の基準：開いて 30 秒で、段の並びと、人を置く関門の場所を言える。
  - 試しの基準：開いたときの画面（操作 0 回）だけで a1・a2 に答えられ、操作 2 回以内で a3 に答えられる。答えが仕様書の `stages`・`roles[].actor`・`nodes[].human`・直しと学びの辺と合う。

### 場面 b：次に何を直すかを決める

- 見る人：改善を回す人（決める役の人、テックリード）。図を何度も見ている。
- 答えたい問い
  - b1：いちばん先に直すべき足りないものはどれか（重さの順）。
  - b2：それは流れのどこ（どのノード・どの検査）で、なぜ足りないか。
  - b3：それを直すと、どの関門・戻り道が働くようになるか。
- 成功の定義
  - 人の基準：次に直す所を 10 秒で言える。
  - 試しの基準：操作 2 回以内で、1 位の足りないものを図の上のノードと結び付けて言え、それが答え合わせの表の 1 位と合う（重さの順は未決の問い 7 の答えで決め、答え合わせの表は仕様書からスクリプトで作る。今の図には順が無いので、今の図の評価では「1 位に届くか」で見る）。理由の文（`gap`）まで操作 3 回以内で届く。

### 場面 c：移行の段階を説明・合意する

- 見る人：決める役の人が、チームや関係者に説明する。聞く側は流れの細部を知らない。
- 答えたい問い
  - c1：今（as-is）と目指す形で、何が違うか（足す・無くす・自動に変わる）。
  - c2：段階ごとに何を足すか、その順番と理由。
  - c3：各段階に、まだ残る足りないものは何か。
- 成功の定義
  - 人の基準：段階ごとの変更を、1 段階 1 文で説明できる。
  - 試しの基準：段階を切り替える操作だけで、各段階で足す・無くす・変わるノードを漏れなく挙げられ、仕様書の `since`・`until`（ノード・検査・gap）と合う。各段階の足りないものの数を言える。

## 変えてはいけないもの

今の図が持っていて、ほかの道具や仕様書が頼っているもの。ナビゲーションの直しでも変えない。

- 外のファイルやネットワークを使わない、単体で開ける 1 ファイル（[7〜15 行](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html#L7-L15)）。
- 埋め込み口：`/*DESIGN*/null` と `/*OVERLAY*/null` の置き換え（create-frontier-team の SKILL.md の進め方の 4「書き出す」）。
- 要素の属性：`data-node-id`・`data-edge-id`・`data-check-id`・`data-role-id`・`data-stage-id`。注記の対象の ID（ノード・辺・検査）の決め方。検査の ID が段階で変わらないこと（#25）。
- version 1・2 の仕様書をそのまま描けること。欠けたキーを足りないものとして描くこと。
- 配置は、すべての段階を合わせて 1 回だけ決める。段階・矢印・注記・（これから足す）見方を切り替えても、カードも線も動かない。
- 足りないものを HTML が数えること（SKILL.md の進め方の 5「確かめる」が、足りないもののタブを見る）。
- 同じ仕様書からは同じ図になること（描画は決まった順）。

画面から分かったこと（棚卸しの判定の根拠）：

- ヘッダーは 3 行で、操作と凡例の印が 20 あまり並ぶ（タブ 4、段階 5、凡例の印 11、チェックボックス 4）。どの場面でも、そのうち半分以上は使わない（01）。

- 「足りないもの」のタブは平らな文の列で、重さの順が無く、図のノードへ戻れない。段階1では、同じ理由（CI がまだ無い）の検査が 3 行に分かれる。
- #25 で、段階の説明（`phases[].note`）と前の段階からの差（足す・無くす・変わる）が、「足りないもの」のタブの先頭に文で出るようになった（07、[791〜800 行](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html#L791-L800)）。ただし、場面 c の情報が場面 b のタブに同居し、キャンバスから見えない。「変わる」は何が変わったかを言わない（目指す形では「チケットに分ける、実装、決定的な検査」とだけ出る）。名前を押しても図へ飛べない。
- 段階の切り替えでは、カードに「＋ この段階で足す」「◇ この段階で変わる」「次の段階で無くなる」の印が付く（05）。前の段階から無くなったものは隠れるだけで、図に跡が残らない（06 と 05 を比べる）。
- 凡例の「人」と「自動」が同じ灰色の印（[161 行](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html#L161)、`session-human` の使い回し）。

## ナビゲーションの案

参考にした考え方（どれも上流の固定した版の SKILL.md を読んだ。文は写していない）：

### 案 A：今のまま、消す候補を消す

棚卸しの「採らない」を消し、凡例を詰める。ヘッダーは 2 行ほどになる。

- 良い点：小さな直しで済む。今の操作に慣れた人が迷わない。
- 弱い点：場面の問いに答える情報（重さの順、段階の差分）が増えない。トグルを積む形は残り、次の不満でまた足すことになる。「核心的な改善ができていない」の原因に触れない。

### 案 B：場面ごとの見方を 3 つにする（推す）

ヘッダーに見方の切り替えを 1 つだけ置く：「全体を掴む」「次に直す」「移行」。見方が、出す印・矢印・凡例・横の一覧を決める。チェックボックスは無くす。配置はどの見方でも同じ（変えてはいけないもの）。

| | 全体を掴む（a） | 次に直す（b） | 移行（c） |
| --- | --- | --- | --- |
| カードの印 | 誰が動かすか、人、種類、関門の形 | ＋ 足りないもの、戻しにくさ、検査のボタン、注記 | ＋ 段階の印（足す・無くなる） |
| 矢印 | データを強く、直し・学びを薄く | 直し・学びを強く、データを薄く | 選んだ段階のものだけ |
| 横の一覧 | 無し（凡例を出す所） | 足りないものを重さの順に。同じ理由はまとめる。行を押すと図のノードが選ばれる | 段階ごとの差分（足す・無くす・変わる・置き換え。「変わる」は何が変わったかつき）と、段階の理由、段階ごとの足りないものの数。行を押すと図のノードが選ばれる |
| 段階の切り替え | 出さない（最後の段階で描く） | 出さない（最後の段階で数える） | 出す |
| 凡例 | この見方で出る印だけ | 同 | 同 |

- 良い点：場面ごとの成功の定義に、見方 1 つで答えられる。足す情報（重さの順、差分）の置き場が決まり、トグルが積もらない。ヘッダーは 1 行に収まる見込み。
- 弱い点：直しが大きい（横の一覧 2 つと、見方ごとの出し分け）。見方を知らない人が「次に直す」を開かない恐れがある（初めの見方の決め方は未決の問い 1）。

### 案 C：場面ごとに別の画面にする

「全体」はキャンバス、「次に直す」は足りないものの表と小さな図、「移行」は段階を左右に並べた図、と画面ごとに配置を変える。

- 良い点：場面ごとにいちばん合う形にできる（たとえば移行は前後を並べて比べられる）。
- 弱い点：同じ流れに配置が 2〜3 通りでき、場面をまたぐと位置で覚えたことが効かない。配置を 1 回だけ決める決まり（変えてはいけないもの）に触れる。直しがいちばん大きい。

推すのは案 B。理由：持ち主の不満（ナビゲーションが複雑）の原因は、場面を決めずにトグルを積んだことで、案 B だけがそれを直す。案 C の良い所（前後の比較）は、案 B の移行の見方の差分の一覧で、配置を変えずに半分は取れる。

## 次の段の段取り

この設計書の成功の定義で、今の図（3e4fc5c）を評価する。直した図ができたら、同じ手順で前と後を比べる。図は直さない。

2. design-critique の 5 観点で見る。「誰向けの何か」には場面を 1 つずつ入れ、段階は「詰め」とする。観点ごとに、成功の定義に照らす。
   - 第一印象：開いたとき最初に目に入るものが、その場面の 1 つめの問い（a1・b1・c1）の答えか。
   - 使いやすさ：場面の問いに答えるまでの操作の数（試しの基準と同じ数え方）。
   - 視覚の階層：読む順が、場面の問いの順と合うか。主な道と戻り道の重さ。
   - 一貫性：同じ見た目が同じ意味か（今は「人」と「自動」が同じ灰色）。同じ情報が 2 か所に出ていないか。
   - アクセシビリティ：場面で使う倍率での文字の大きさ（全体で 9px 以下）、色だけで分けている印。
   - 指摘は重さを 3 段で付け、影響の大きい順に 3 つの直し方を書く。
3. 人物像を決めたエージェントに、場面の作業をさせる（adversarial-ux-test の考え方）。1 場面に 1 人。各エージェントには図の HTML だけを渡し、仕様書・設計書・この文書は渡さない。ブラウザで操作させ、操作の回数と答えを記録させる。
   - a：2 週間前に入ったエンジニア。仕様書は読んでいない。「5 分で分からなければ、人に聞く」。作業：a1〜a3 に答える。
   - b：テックリード。週に 1 回、10 分だけ改善の時間がある。「次に直すものを 1 つ決めて、チケットにしたい」。作業：b1〜b3 に答え、チケットの題を書く。
   - c：プロダクトオーナー。関係者に移行を説明する。流れの語（関門、直しの辺）は知らない。作業：c1〜c3 を、段階ごとに 1 文で書く。
   - 答えを 1 の答え合わせの表と照らし、試しの基準の合・否を付ける。
   - 不満は人物の声で書かせたあと、別の目で 4 つに仕分ける：誰でも困る（直す）、その人物だけ（記す）、人物の癖（捨てる）、要望（考える）。仕分けを通ったものだけを、直しの案にする。
4. 2 と 3 を表にまとめる：場面 × 成功の定義（人の基準・試しの基準）× 合・否 × 根拠（画面、操作の記録）。人の基準は持ち主が見て付ける。
5. 結果を PR の本文に書き、直す順の案を出す。この設計書の問いや判定が試しで外れていたら、ここを直す。
