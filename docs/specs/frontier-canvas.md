## 目的

図は #21〜#25 で、出てきた不満（線が複雑、文章が多い、関門の中が見えない、段階、人の作業の「スキル無し」）を 1 つずつ直してきた。そのたびにトグル、印、タブ、窓が増え、「図はだいぶ良くなったが、ナビゲーションが複雑になってきた」（持ち主、2026-11-15）。

原因は、図が「誰が・どの場面で・何を答えるために開くか」を決めないまま、全部を 1 枚でこなそうとしてきたこと。成功の定義も無い。create-frontier-team は「設計書から作る」と言いながら、図そのものには設計書が無かった。

2 つの層に分けるのは、持ち主の次の声による（2026-11-15）。

- 「表示する情報の整理と見せ方があると思うので、それぞれ詰めていきたい」
- 「ナビゲーションに出ている内容はグルーピングを文字で説明していて、デザインで解決できる内容だと思う」「既存のに引っ張られて足し算しがちで、要素が削れていない」「今の見た目も好きではあるが、ごちゃつき具合が気になる」

情報の層で「場面ごとに何が要るか」を決め、見せ方の層では今の図に引っ張られずに、要る情報だけを見た目で伝える形を決める。

進め方：(1) 情報の層を決める（済み、下書きとして確定）。(2) 見せ方の層を、場面 a（既定の見方）から決める。モックを白紙から作って比べる。b・c は a が決まってから。(3) 決まった成功の定義で、今の図とモックを評価する（[評価の段取り](#評価の段取り)）。(4) 図を直す（その次の PR）。

## 変えてはいけないもの

今の図が持っていて、ほかの道具や仕様書が頼っているもの。見せ方を作り直しても変えない。

- 外のファイルやネットワークを使わない、単体で開ける 1 ファイル（[7〜15 行](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html#L7-L15)）。
- 埋め込み口：`/*DESIGN*/null` と `/*OVERLAY*/null` の置き換え（create-frontier-team の SKILL.md の進め方の 4「書き出す」）。
- 要素の属性：`data-node-id`・`data-edge-id`・`data-check-id`・`data-role-id`・`data-stage-id`。注記の対象の ID（ノード・辺・検査）の決め方。検査の ID が段階で変わらないこと（#25）。
- version 1・2 の仕様書をそのまま描けること。欠けたキーを足りないものとして描くこと。
- 足りないものを HTML が数えること（SKILL.md の進め方の 5「確かめる」が、足りないものを見る）。
- 同じ仕様書からは同じ図になること（描画は決まった順）。
- 配置は 1 回だけ決め、見方・段階・注記を切り替えても、ノードも線も動かない。構図（役割の行 × 段の列）は[見せ方の層](#どの見方にも共通)で決めたとおりで、どの見方でも同じにする。

## 第 1 層：情報（何を出すか）

下書きとして確定（持ち主、2026-11-15「だいたい良さそう」）。直すのは、見せ方を詰める中や評価で外れが見つかったときだけにする（[情報の層の未決](#未決の問い)）。

### 図を開く場面

持ち主が確かめた 3 つの場面。

成功の定義は 2 段で書く。「人の基準」は持ち主が見て判定する。「試しの基準」は、人物像を決めたエージェントに図だけを渡して判定する（[評価の段取り](#評価の段取り)）。エージェントは秒を測れないので、試しの基準は「操作の回数」と「答えが仕様書と合うか」で書く。操作の数え方：クリックとキーを押すのは 1 回ずつ、一続きのスクロール・ドラッグ・ズームは 1 回、カーソルを当てるだけは数えない。「開いたとき」は、その場面の見方を選んだ状態から数える（既定の見方は a。b・c は、切り替えの 1 回を足す）。

#### 場面 a：流れの全体を初めて掴む

- 見る人：チームに新しく入った人。久しぶりに見る本人。仕様書の JSON も設計書も読んでいない。
- 答えたい問い
  - a1：流れは何段で、どこから始まり、どこで終わるか。
  - a2：人はどこで関わるか（人がやる・条件で人・エージェントがやる・自動）。流れは何をきっかけに、誰が始めるか。
  - a3：どこで判定し、通らなければどこへ戻すか（関門と戻り道）。
- 成功の定義
  - 人の基準：開いて 30 秒で、段の並びと、人がやる所・条件で人の所・きっかけを言える。
  - 試しの基準：開いたときの画面（操作 0 回）だけで a1・a2 に答えられ、操作 2 回以内で a3 に答えられる。答えが仕様書の `stages`・`triggers`・[人の関わり](#人の関わりときっかけ)の導き方の結果・直しと学びの辺と合う。

#### 場面 b：次に何を直すかを決める

- 見る人：改善を回す人（決める役の人、テックリード）。図を何度も見ている。
- 答えたい問い
  - b1：いちばん先に直すべき足りないものはどれか（重さの順）。
  - b2：それは流れのどこ（どのノード・どの検査）で、なぜ足りないか。
  - b3：それを直すと、どの関門・戻り道が働くようになるか。
- 成功の定義
  - 人の基準：次に直す所を 10 秒で言える。
  - 試しの基準：操作 2 回以内で、1 位の足りないものを図の上のノードと結び付けて言え、それが答え合わせの表の 1 位と合う（重さの順は[決まったこと](#決まったこと)の 7。答え合わせの表は仕様書からスクリプトで作る。今の図には順が無いので、今の図の評価では「1 位に届くか」で見る）。理由の文（`gap`）まで操作 3 回以内で届く。

#### 場面 c：移行の段階を説明・合意する

- 見る人：決める役の人が、チームや関係者に説明する。聞く側は流れの細部を知らない。
- 答えたい問い
  - c1：今（as-is）と目指す形で、何が違うか（足す・無くす・自動に変わる）。
  - c2：段階ごとに何を足すか、その順番と理由。
  - c3：各段階に、まだ残る足りないものは何か。
- 成功の定義
  - 人の基準：段階ごとの変更を、1 段階 1 文で説明できる。
  - 試しの基準：段階を切り替える操作だけで、各段階で足す・無くす・変わるノードを漏れなく挙げられ、仕様書の `since`・`until`（ノード・検査・gap）と合う。各段階の足りないものの数と中身を言える（2026-11-16 に「中身」を足した。評価で、説明する人は数ではなく中身を聞かれ、数だけでは推測で外すと分かったため）。

### 人の関わりときっかけ

2026-11-15 に足した。1 の 4 つの見分け、2 のきっかけ、6 のフェーズは持ち主が決めた（[決まったこと](#決まったこと)の 11〜16）。持ち主の声：「今はマージを人がやるんですっけ？ 条件による気がします」「トリガーとなるインプットも人が渡していますかね？」「人がやること、人かエージェントがやること、エージェントがやることで見分けられると嬉しいのかも」。

場面 a のモック（a2-r2）の見出し「人が判断するのはマージの 1 か所だけ」は、誤解を招いていた。上流（原則・仕様・規約）は決める役の人が決めている（エージェントは下書きをする）。流れを始める依頼も人が渡している。マージは、実際のチームでは条件で変わることが多い（公開・移行・広い変更なら人、ほかは検査が通れば自動かエージェント）。また、カードの札（計画・実行）は「どのセッションか」で、「人がどれだけ関わるか」ではない。問い a2 の「人の場所」に答えるのは後者。

#### 1. 主な見分けは「人の関わり」

ノードを 4 つに分ける。持ち主の 3 つ（人・人かエージェント・エージェント）を主にし、自動はエージェントの側の静かな見た目で分ける。

| 人の関わり | 意味 | 仕様書からの導き方（上から順に、最初に当たったもの） |
| --- | --- | --- |
| 条件で人 | 条件を満たすと人、ほかはエージェントか自動 | 1. 選んだ段階で `human_if` が在る |
| 人がやる | 人が手を動かすか決める | 2. `human` が true か、`session` が human<br>3. 上流（`layer` が upstream）で、行が決める役（`roles[].decides`）<br>5. 人の行（`actor` が human）で `session` を省いた、コードでも関門でもない作業（今の図の [271 行](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html#L271) と同じ） |
| エージェントがやる | 計画か実行のセッション | 4. `session` が plan か run |
| 自動 | コード・スクリプト・CI | 6. ほかすべて |

- 上流の扱い：SKILL.md は上流に `human` を付けないと決めている（「上流は流れへの入力で、途中の確認ではない（`session` は plan にし、`human` は付けない）」）。`human` は「流れの途中に人を置く関門」の意味なので、この決まりは変えない。上流が「人がやる」になるのは 3 の導き方による。`session` が plan のままなのは、エージェントが下書きをするから（選んだときの詳細に「人がやる（エージェントが下書き）」と出す）。
- 条件で人のカード：名前の下の 1 行に条件の文を短く出す（長ければ … で切り、全文は選んだときの詳細）。札の「条件で人」だけでは「どんな時に人か」に答えられないから。
- エージェントの計画・実行の区別：場面 a のカードには出さず、選んだときの詳細に出す。理由：札が「計画」「実行」だと、それがエージェントだと読むのに凡例が要る（札が自分で言わない）。場面 a の問いは人の関わりで、計画と実行の違いはスキルやセッションの分け方を直す場面 b の関心だから。カードの札は「エージェント」の 1 語にする。
- 自動はエージェントと札も枠も分ける（破線の枠と灰色の「自動」）。持ち主の 3 つには入らないが、スキルが要らない所（足りないものにならない所）なので、場面 b で効く。

#### 2. きっかけ

流れの最初に、誰が何を渡して始まるかを出す：人が依頼を渡す／定期／イベント（PR が開いた、など）。きっかけが入るノードの上に、短い矢印と 1 行の文字で出す。きっかけのためにノードや列を足さない（配置を動かさない）。人のきっかけは人の関わりと同じ色にする。

#### 3. 見出しの文の規則

場面 a の見出しは、人の関わりから規則で作る。手で書いた文にしない。

- 頭に「{最後の段階の名前}：」（`phases` が無ければ付けない）。どの段階の図かを見出しで言う。下の 1 行には段階の名前を重ねない（2026-11-16 に足した。評価で、開いたときに今の図か将来の図か分からないという不満が 6 回のうち 4 回出たため）。
- 「{最初の段}から{最後の段}まで {段の数} 段。」
- 続けて「人がやるのは{A}と{B}…、{C}は条件で人。」A は人のきっかけの `label`。B は、入力のまとまり（`group` が input の段。`group` の無い仕様書では、ノードがすべて上流の段）のノードがすべて「人がやる」なら「入力の {段の数} 段」、ほかの「人がやる」ノードは段の名前。C は「条件で人」のノードの段の名前。
- 人がやる所が無く条件で人だけなら「人は{C}で条件つきで関わる。」、どちらも無ければ「人は関わらない。」。
- その下の 1 行：チーム・リポジトリと、カードの数（人・条件で人・エージェント・自動）。
- そらまめ（目指す形）：「目指す形：要求・原則から評価まで 8 段。人がやるのは機能の依頼と入力の 3 段、マージは条件で人。」

#### 4. 仕様書のキー（足すのは最小に）

今の `session`・`human`・`layer`・`roles[].decides`・`actor` から読み替えられるものは読み替え、足りない 2 つだけを足す（フェーズの `stages[].group` は [6](#6-フェーズ)）。どちらも省いてよく、省けば今と同じに描く。

- ノードの `human_if`：条件の文。`"文"` か、`gap` と同じ `{"text","since","until"}` の形（段階で変わるとき）。`human` は true のまま残す（条件を満たしたときに人を置く関門であることは変わらない）。条件を満たさないときに誰が通すかは、条件の文に書く。
- 最上位の `triggers`：`[{"to":"ノードの id","by":"human | schedule | event","role":"役割の id（human のとき）","label":"機能の依頼"}]`。`to` のノードが選んだ段階に無ければ出さない。

version 2 の仕様書はそのまま描ける：`human_if` が無ければ 1 の導き方の 2 以降で決まり、`triggers` が無ければきっかけを出さない。今の図（3e4fc5c）は知らないキーを読まないので、足したキーがあっても今と同じに描く（`human` を文字列にすると、今の図は `human === true` で数えるため、人の関門が 0 か所・戻せない関門に人がいない、と足りないものを誤って出す。これが `human` に文字列を許さない理由）。

選ばなかった案：

- `human` に条件の文字列を許す：キーは 1 つで済むが、今の図と、それで描いた画面が誤った足りないものを出す（上の理由）。
- 上流のノードに `human: true` を付ける：SKILL.md の決まりを変え、「人を置く関門は 1 か所」の数え方（[779 行](https://github.com/degwinthegreat/skills/blob/3e4fc5cd648ff79bd7521c9bf7c31b1c67f6e374/create-frontier-team/canvas.html#L779)）とぶつかる。
- ノードに人の関わりのキー（`involve` など）を足す：今のキーから導けるものを二重に書くことになり、食い違ったときにどちらが正しいか決まらない。
- きっかけを最初の列の前の 1 列として出す：配置が動き、見方の切り替えで位置が変わらない決まりに合わない。

#### 5. そらまめの例

[frontier-canvas/soramame.json](frontier-canvas/soramame.json) を直した（どれも架空）。

- きっかけ：プロダクトオーナーが「機能の依頼」を仕様に渡す（人）。指標を集めるのは毎週（定期）。
- マージ：段階2から条件で人（「移行・削除・決済を含む差分のとき（データの移行、データの削除、決済）。ほかは必須のチェックが緑なら自動でマージする」。カードには「移行・削除・決済…」のように頭だけが出るので、条件の文は短い言い方から書き始める）。今・段階1は、すべての差分を人が読む検査があり、人がやる。
- 上流：キーは変えていない。3 の導き方で「人がやる」になる。
- フェーズ：入力＝1〜3（上流の段。きっかけもここに入る）、振り分け＝4 分ける（worktree に配るは 5 の段だが、同じ振り分けの働き）、候補＝5 実行・6 検証、出力＝7 マージ・8 評価。

#### 6. フェーズ

持ち主の声：「graph engineering だと input・routing・candidate・output でフェーズを分けていたりする。他にもいいフェーズ分けがあるかもしれないが、そういった流れが見えるといい」。

8 つの段の上に、大きなまとまりを 4 つ置く：**入力・振り分け・候補・出力**（graph engineering の input → routing → candidate → output）。入力が振り分けで並列の担当に広がり、候補が出て、選ばれて出力になる。人の関わりと噛み合う：人は入力と出力にいて、エージェントと自動は真ん中にいる。場面 a で、これが 1 画面で見えるとよい。

- 仕様書：`stages[]` に `group`（`input | routing | candidate | output`）を省いてよいキーとして足す。省いた段はフェーズの行に出さない（推測で埋めない）。同じフェーズが続く段を 1 つのまとまりにする。キーの名前は `group`（[決まったこと](#決まったこと)の 16）。
- 見せ方：段の番号の上に、段の列をまたぐ薄い 1 行（文字と細い線）。色の面にしない。凡例は足さない。
- 上流と入力：上流（`layer` が upstream）は、入力のまとまりと同じもの（SKILL.md でも「上流は流れへの入力」）。同じものに同じ語を使い、図では「入力」と呼ぶ。段の下の「上流」の印は出さない。`layer` のキーはそのまま残す（人の関わりの導き方 3 と、場面 b の足りないものの数え方が使う）。SKILL.md の説明で「上流＝入力のまとまり」とそろえるのは、図の直しの PR でする。

選ばなかった分け方：

- DECIDE・MAKE・DELIVER・GROW（決める・作る・届ける・育てる）：人の言葉で分かりやすいが、「振り分け」が「作る」に溶けて、並列に広がって候補から選ぶ形が見えない。
- 段そのものを減らしてフェーズにする：段（8 つ）はスキルとセッションの単位で、場面 b・c で要る。段は残し、上にまとまりを重ねる。
- フェーズを図が段の名前から推測する：チームごとに段の名前が違い、外れたときに直す場所が無い。

### どの見方にも共通

- **構図**：役割の行 × 段の列。1 画面に全体を出す。配置と線の割り当ては、全段階のノードと全種類の辺（データ・直し・学び）を合わせて 1 回だけ決め、見方と段階では出す・隠すだけにする（カードも線も動かない）。
- **見出し**：答えを言う 1 文を、仕様書から規則で作る（手で書いた文にしない）。見方ごとの文は下に書く。その下に 1 行（チーム・リポジトリ、段階、数）。ゴシック、濃い灰色。
- **段**：番号と名前。上流の印は出さない（上流は入力のまとまりと同じもの）。
- **役割の行**：罫で区切らず、暖かい薄い灰色の地を 1 行おきに敷く（左端は見出しに揃える）。左の余白に役割の名前と人数。
- **カード**：白地、角丸、ごく弱い影。名前が主役（太字）で、名前の下に 1 行（スキル名を等幅で。条件で人のカードは条件の文。長ければ … で切る）。種類（分ける・コード・関門）とカードの左の色の線は出さない。
- **カードの名前は 14px 以上**：1440×900 で、a は 1 倍（17px）。b・c は右の一覧のぶん図が 0.84 倍になり、14.3px。1280×800 の b・c は図が 0.73 倍になるので、そのときだけ名前の字を大きくして 14px 以上にする（見せ方 V1、2026-11-16。名前は 2 行に折れやすくなる）。
- **地と色**：地はごく薄い暖かい白。人の関わりの色は、目を引きすぎない、彩度を抑えたアンバー〜テラコッタ（持ち主「人を表す赤が注意を引きすぎる」。a2-r4 までは人を朱にしていた）。エージェントは彩度を抑えた青。自動は灰色。
- **赤は b の 1 位だけ**に使う（下の b）。赤は「問題・危ない」を言う色なので、a・c と、b の 2 位以下には使わない。
- **線**：直角に折り、角を丸める。出入りの口をずらし、1 点に集めない。データの線は暖かい灰色で細く、a の主な道（最初の段から最後の段までの、データの線の最長の道）だけ濃くする。
- **注記**（決まったこと 6）：a・b で、カードの下の端に下げる小さな白い札（「✎ 差し戻し 12%」）。色を使わない。c では出さない。
- **凡例は置かない**。分類は、札の文字・枠の線の種類・位置で、その場で読めるようにする。

- **戻り道の線は選んだときだけ**：既定では、戻り先のカードの下の「直しで戻る 2 本」の文字だけにする（2026-11-16 に「戻る：直し 2」から改めた。2 が数か番号か読めなかったため。学びもあれば「直しで戻る 2 本・学びで戻る 1 本」）（全部の線を出すと、図の下に破線の束ができてうるさい）。線は、選んだカードと、一覧で選んだ足りないものにつながる分だけ出す。直しは破線、学びは点線（色は変えない）。元のカードの右から、図の下の通り道を通り、戻り先のカードの下に入る。

### c 移行

- **段階の切り替えは c の中だけ**。右の一覧に段階を並べ、それぞれに理由（`phases[].note`）と足りないものの数を添えて比べられるようにする。押すと段階を切り替える。
- **選んだ段階の足りないものの中身**（2026-11-16 に足した。問い c3）：選んでいる段階の行の中に、その段階に残る足りないものを、b と同じまとめ方（同じ理由は 1 行、重さの順）で並べる。ほかの段階の行は数だけ。赤は使わない。1280×800 でも、一覧をスクロールせずに見える。
- **選んだ段階は、ほかの見方へ移っても残す**（hash の `p=`。2026-11-16）。a・b の判定には使わない（a は最後の段階、b は今の段階）。
- **見出し**：「{段階の名前}：{1 文}。」。1 文は前の段階からの差から規則で作る（置き換える・足す・無くす・変わる・線）。その下に `phases[].note` と足りないものの数。
  - 段階1：「人のレビューを決定的な検査・レビューに置き換える。」
  - 段階2：「決定的な検査・マージが変わる。」（中身は一覧：テスト・型・lint の足りないものが埋まった／予約の通しテストが増えた／すべての差分を読む検査が無くなった／人 → 条件で人）
  - 目指す形：「worktree に配る ほか 3 つを足す、決定的な検査が変わる、線 1 本が無くなる。」
- **無くなるカードと置き換わるカードを見せる**：
  - 直前の段階から無くなったカードは、同じ場所に薄い破線の枠と取り消し線の名前で残し、左上に「無くなる」と書く。無くなった線は薄い点線で残す。それより前の段階で無くなったものは出さない。
  - 置き換えで入ったカードは左上に「⇄ 置き換え」、足したカードは「＋ 足す」、変わったカードは「△ 変わる」。色は使わない（赤は b、人の色は人の関わり）。
  - 理由：c1・c2 は「この段階で何が変わるか」で、跡が無いと置き換えが「足す」にしか見えない（今の図の 06 と 05）。全部の段階の跡を重ねると、段階が進むほど図が跡で埋まる。
- **右の一覧の下**：前の段階からの差（置き換えは 1 行、足す・無くす・変わる（何が変わったか）・線）を並べ、押すとカードを選ぶ。
- 人の関わりの札は出さない（c では ○。人の枠の色だけ残す）。

### 詳細の窓

カードを選ぶ（押す、一覧で選ぶ、キーボードで Enter）と出す。題はカードと同じ短い名前で、題名の全文が違えばその下に添える（図と表を照らし合わせられるように。2026-11-16）。2 つ以上あるもの（足りないもの・戻り道・戻し先）は「／」でつながず、1 行ずつ書く（2026-11-16）。中身は見方ごとに、その場面で ○ の情報：a は関わり・スキル・成果物・受け取る・渡す（関門なら判定と「通らなければ ○○へ戻す」、直しで戻ってくるカードなら「直しで戻る」。2026-11-16）、b は関わり・戻しにくさ・判定・足りないもの・中の検査（検査ごとに、動かすもの・判定・足りない理由）・戻り道・注記、c はこの段階での変化・在る段階。

- **選んだカード、その戻り道、戻り先のカードを隠さない**。選んだカードと線でつながるカード、見出しと段の名前の帯も隠さない。
- 図の下の空きに横長で収まるなら、そこに浮かせずに出す（段組みで横に流す）。
- 収まらなければ、隠さないものに重ならず、ほかのカードにもなるべく重ならない所を探して浮かせる。右の一覧には重ねない。
- 画面の大きさが変わったら置き直す。1440×900 と 1280×800 で、a・b・c のどのカードを選んでも上を満たすことを確かめる（a2-r7 で確かめた）。

### 操作

見方の切り替え・一覧・詳細の窓・図のカードを、キーボードとスクリーンリーダーで使えるようにする。振る舞いは UI SDK（[vercel-labs/ui@98ba9fd](https://github.com/vercel-labs/ui/tree/98ba9fd019274efae63fae08eb56da02453b4873)）を手本にする。依存にはしない（図は外のファイルを読まない 1 ファイルなので）。コードは写さない。

- **見方の切り替え：tablist**。3 つの tab で、選んだものに `aria-selected`。← → で隣の見方へ移って切り替え、Home・End で端へ。Tab で止まるのは選んでいる tab 1 つ（roving focus）。見方は URL の hash にも持ち、開き直すと同じ見方・段階・選んだカードに戻る（モックは `#b&sel=n9` の形）。
- **一覧：listbox**。b の足りないもの、c の段階、c の差は、それぞれ listbox と option。↑ ↓ で移り（roving focus）、Enter で選ぶ（b・c の差はカードを選ぶ、c の段階は段階を切り替える）。今の段階と、選んでいる行に `aria-selected`。重さの段の区切り（戻しにくさ など）は group の名前にする。
- **図のカード：roving focus**。図は Tab で止まるのが 1 か所で、中は矢印キーで動く（← → は同じ行の隣のカード、↑ ↓ は近い行のカード）。Enter・Space で選び、Esc で選びを外す。カードは button 役で、名前に「名前・関わり・段・役割」（b は足りないもの、c は段階での変化も）を入れる。選んだカードに `aria-expanded`。
- **詳細の窓：popover**。モーダルにしない（図を見ながら読むため）。開いてもフォーカスは選んだカードに残し、Tab で窓の中へ入れる。Esc で閉じてカードへ戻す。窓の外を押すと閉じる。窓の題はカードの短い名前（2026-11-16 に「題名」から改めた。題名は題の下に添える）。
- **表：ページそのものがスクロールする**（2026-11-16）。中の箱だけが動く形にしない。ホイール・PageDown・End で動き、表に Tab で入れる。
- **読み上げ**：見方・段階を切り替えたとき、見出しの 1 文を polite な live region で読む。
- **色だけで分けない**：関わりは札の文字と枠の線の種類、足りないものは名前の下の文字、戻り道は線の種類でも分かる。
- **試験**：ブラウザを headless で動かす試験を、図の直しの PR に置く。
  - Tab の順：見方の切り替え → 図 → 一覧 → 詳細の窓。
  - 役と名前：tablist・tab・listbox・option・カードの button・窓の題が、決めたとおりに付いている。
  - キーボードだけで、3 つの見方・c の段階・カードの選択と Esc での戻りができる。
  - hash で開き直すと、同じ状態に戻る。
  - 1440×900 と 1280×800 で、詳細の窓が選んだカード・戻り道・戻り先に重ならない。
  - 1440×900 で、どの見方でもカードの名前が 14px 以上。1280×800 の b・c でも、一覧を出したままで 14px 以上（2026-11-16）。

### 見せ方の原則

持ち主の声（[目的](#目的)）から。これからの直しの物差しにする。

- 分類（行・段・関わり・関門など）は、位置・形・線の種類・文字で伝える。凡例や説明の文で伝えない。
- 見方ごとに、その場面で ◎ の情報だけを置く。○ は操作で出す（選ぶ、見方を変える）。－ は置かない。
- 足し算をしない。直すたびに、画面の要素の数を数えて前と比べる。
- 同じ情報を 2 か所に出さない。
- 強い色は意味を 1 つだけ持つ（人の色＝人の関わり、赤＝b の 1 位）。

手順：

1. 材料をそろえる。[frontier-canvas/soramame.json](frontier-canvas/soramame.json) を図に埋め込む（SKILL.md の進め方の 4 の python の 1 行）。答え合わせの表を、仕様書からスクリプトで作る：段の並び、人を置く関門、直し・学びの辺、段階ごとの足す・無くす・変わるノード（変わったのは検査か gap か矢印か）、段階ごとの足りないもの。答え合わせは図の描画に頼らない。
2. design-critique の 5 観点で見る。「誰向けの何か」には場面を 1 つずつ入れ、段階は「詰め」とする。観点ごとに、成功の定義に照らす。
   - 第一印象：開いたとき最初に目に入るものが、その場面の 1 つめの問い（a1・b1・c1）の答えか。
   - 使いやすさ：場面の問いに答えるまでの操作の数（試しの基準と同じ数え方）。
   - 視覚の階層：読む順が、場面の問いの順と合うか。主な道と戻り道の重さ。
   - 一貫性：同じ見た目が同じ意味か。同じ情報が 2 か所に出ていないか。
   - アクセシビリティ：場面で使う倍率での文字の大きさ、色だけで分けている印。
   - 指摘は重さを 3 段で付け、影響の大きい順に 3 つの直し方を書く。
3. 人物像を決めたエージェントに、場面の作業をさせる。1 場面に 1 人。各エージェントには図の HTML だけを渡し、仕様書・設計書は渡さない。ブラウザで操作させ、操作の回数と答えを記録させる。
   - a：2 週間前に入ったエンジニア。仕様書は読んでいない。「5 分で分からなければ、人に聞く」。作業：a1〜a3 に答える。
   - b：テックリード。週に 1 回、10 分だけ改善の時間がある。「次に直すものを 1 つ決めて、チケットにしたい」。作業：b1〜b3 に答え、チケットの題を書く。
   - c：プロダクトオーナー。関係者に移行を説明する。流れの語（関門、直しの辺）は知らない。作業：c1〜c3 を、段階ごとに 1 文で書く。
   - 答えを 1 の答え合わせの表と照らし、試しの基準の合・否を付ける。
   - 不満は人物の声で書かせたあと、別の目で 4 つに仕分ける：誰でも困る（直す）、その人物だけ（記す）、人物の癖（捨てる）、要望（考える）。仕分けを通ったものだけを、直しの案にする。
4. 2 と 3 を表にまとめる：場面 × 成功の定義（人の基準・試しの基準）× 合・否 × 根拠（画面、操作の記録）。人の基準は持ち主が見て付ける。
5. 結果を PR の本文に書き、直す順の案を出す。情報の層の判定が試しで外れていたら、そこを直す。
