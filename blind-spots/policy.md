# blind-spots の方針

blind-spots（人が確かめるのをやめた所を見つけるスキル。名前は仮）を設計するときの方針。ルールの採否（decisions.md）は、ここの項目番号で理由を書く。

この方針では、人が確かめずに通したもの、見るのをやめたもの、手で避けているものをまとめて「手放した所」と呼ぶ。

- 決めた人と日付：持ち主（2026-11-11）。
  - 持ち主が決めたもの：問題意識（解決したいことの元）、P4 の持ち運びの条件、P5 の retro・improve-intent-skill との境界、名前を既存の語で言うこと。
  - エージェントが提案し、持ち主が賛成したもの：P1〜P3 の3つの方法（週に一問、速く通したものの抜き取り、任せた度合いの数）。賛成は方法の骨組みに対するもので、下の文の言い回しや細かい条件は下書き。
  - 下書きのまま（持ち主の確認待ち）：解決したいことの3つの文、P3 の後半、P6、非目標の3〜5番目、譲る順、名前の案。

## 解決したいこと

- 履歴につまずきとして残らない、人が手放した所を見つけ、改善の候補として示す。根拠：持ち主 2026-11-11（問題意識。改善の伸び代は、人が認知を諦めて手放した所にある）。
- 人に聞くだけでは、本人が手放したと気づいていない所は出てこないので、記録から速く通したものを選んで確かめ、手放した所に問題が残っているかを裏付ける。根拠：持ち主 2026-11-11（問題意識。アンケートしか方法を思いつかない）、エージェントの提案2に持ち主が賛成。
- 見つけたものを直す仕事は、ほかのスキルに渡せる形にする。根拠：持ち主 2026-11-11（境界の条件）。

## 方針

- **P1. 週に一問だけ聞く。** 問いは、今週、確かめずに通したもの、見るのをやめたもの、手で避けているもの。答えが無くてもよい。根拠：エージェントの提案1に持ち主が賛成（2026-11-11）。「答えが無くてもよい」は推測。
- **P2. 速く通したものを抜き取って確かめる。** 週に2〜3件を選ぶ。選ぶのは、長い報告にすぐマージを返したもの、推奨のとおりに任せたもの。選んだものを、文脈を引き継がない別のエージェントに確かめさせる。問題が見つかれば、そこを手放した所として示す。根拠：エージェントの提案2に持ち主が賛成（2026-11-11）。
- **P3. 任せた度合いの数は、記録の道具がある環境でだけ使う。** 数は、推奨のまま通した割合、承認までの時間と報告の大きさ。使い方は local.md に書く。根拠：エージェントの提案3に持ち主が賛成（2026-11-11）。数（時間、長さ、割合）は道具の出力だけを使い、モデルに記録から数えさせたり写させたりしない。P2 で選んだ理由に数を書くときも同じ。根拠：create-intent-skill/SKILL.md の手順1の2。この後半は推測（持ち主の確認待ち）。
- **P4. 本体は、どの環境にもある材料だけで動く。** 材料は、Claude Code のセッションの記録（`~/.claude/projects` の jsonl）、git、プルリクエストの履歴。手元の道具の使い方は、create-intent-skill と同じく local.md で足す。道具の名前は公開のファイルに書かない。根拠：持ち主 2026-11-11（持ち運べる形の条件）、create-intent-skill/SKILL.md の冒頭と README の「local.md（任意）」。
- **P5. 見つけたものは直さず、渡す。** スキルが原因なら improve-intent-skill に渡す。作業の進め方の改善なら retro に渡す。根拠：持ち主 2026-11-11（境界の条件）。どちらに渡すかの分け方は推測。
- **P6. 小さく始める。** 最初は P1 と P2 だけを入れる。足すのは、使って同じ失敗が2回起きてから。根拠：create-intent-skill/policy.md の P4。推測（持ち主の確認待ち）。

## 非目標

- 履歴に残ったつまずき（手戻り、レビューの往復、エラー）から学ぶこと。それは retro の仕事。このスキルは、履歴に残らない手放した所を見る。根拠：持ち主 2026-11-11（境界の条件）。
- スキルを直すこと、見つけたものを直すこと。スキルの直しは improve-intent-skill、ほかは retro に渡す（P5）。根拠：持ち主 2026-11-11（境界の条件）。
- 手放したこと自体を減らすこと、人に全部を確かめ直させること。手放すのは多くの場合正しい。見るのは、手放した所に問題が残っているかだけ。推測。
- 長いアンケートを取ること。問いは週に一つ（P1）。根拠：エージェントの提案1に持ち主が賛成（2026-11-11）。週に一つに絞る理由（答える手間が増えると答えなくなる）は推測。
- 評価のループ（スキルあり・なしで並べて実行し、採点する仕組み）を組むこと。P2 の確かめは、選んだものを1件ずつ見るだけで、採点しない。根拠：create-intent-skill/policy.md の非目標（同じ線引き）。

## 譲る順

方針どうしがぶつかったら、上から先に譲る。すべて推測（持ち主の確認待ち）。

1. 網羅性（手放した所を全部見つけること）。週に一問と2〜3件の抜き取りで足りる。
2. 数による裏付け（P3）。道具が無い環境では飛ばす。
3. 人の手間の少なさ（問いを一つ、抜き取りを2〜3件に抑えること）。
4. 持ち運べること（P4）。
5. 意思（履歴に残らない、手放した所を見つけること）。最後まで譲らない。

次の3つは譲る対象にしない（どの場合も守る）：公開のファイルに手元の道具の名前を書かない、見つけたものをこのスキルで直さない、数を推測で埋めない。
