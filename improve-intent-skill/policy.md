# improve-intent-skill の方針

improve-intent-skill（既存のスキルを、使って起きた失敗をもとに直すスキル）を設計するときの方針。ルールの採否（decisions.md）は、ここの項目番号で理由を書く。

- 決めた人と日付：持ち主（2026-11-11）。
  - 持ち主が決めたもの：P1〜P6 の骨組み（5つの段階、create-intent-skill とは別のスキルにすること、policy.md と decisions.md の形を共通にすること、参照先を探す JOB）、P3 の概念の圧縮。
  - エージェントが下書きし、持ち主が OK したもの：解決したいことの文、P7、非目標、名前（improve-intent-skill）。
  - 持ち主が直したもの：譲る順の1番目。
  - エージェントが下書きし、下書きのまま進めたもの：譲る順の2〜5番目。

## 解決したいこと

- スキルを使って実際に起きた失敗を記録から集め、原因に合う最小の変更で直す。根拠：持ち主 2026-11-11（骨組みの2・3）。
- 直すたびに指示が足されて本文が伸び、元の意図から筋がぶれていくのを止める。根拠：持ち主 2026-11-11（骨組みの1・3）、create-intent-skill/policy.md の P1・P2。
- どの変更がどの失敗のためのもので、効いたのかを、後から読む人が追えるようにする。根拠：持ち主 2026-11-11（骨組みの4・5）。

## 方針

- **P1. 直す前に意図を取り戻す。** 対象のスキルに policy.md があれば読む。無ければ、本文から「解決したいこと」を下書きして、人に確かめる（create-intent-skill の手順1と同じ）。根拠：持ち主 2026-11-11（骨組みの1）。
- **P2. 起きた失敗だけを直す。** 材料は、作業の手戻りやレビューの往復の回数、人の却下・中断・言い直し、プルリクエストのレビューのコメント、ふりかえり。推測の失敗は材料にしない。同じ失敗が2回起きていなければ直さない。根拠：持ち主 2026-11-11（骨組みの2）、create-intent-skill/SKILL.md の手順6。
- **P3. 原因を分け、上から順に当てる。**
  1. 指示が埋もれて読まれていない → 削るか、上に移す
  2. モデルが言われなくてもやる → 削る
  3. 指示が間違っている → 直す
  4. 指示が足りない → 足す（最後の手段）
  5. 機械で判定できる → 仕組みにする

  足す前に、削れないかを必ず見る。削る・直すときは、概念を圧縮する：概念の数を減らす、同じものには同じ語を使う、新しい語を作らない。概念が少ないほど、読む側の負荷が下がり、誤解が減る。根拠：持ち主 2026-11-11（骨組みの3、概念の圧縮）、create-intent-skill/policy.md の P2・P3。
- **P4. 変更ごとに記録する。** 変更ごとに、理由と、どの失敗に対応するかを decisions.md に残す。前の判断は消さず、superseded にする。根拠：持ち主 2026-11-11（骨組みの4）。
- **P5. 直したら確かめる。** 失敗した場面を、直したスキルでもう一度やらせる。本文の読み手のテストをする。そのあとは、使いながら数字を見る。根拠：持ち主 2026-11-11（骨組みの5）、create-intent-skill/SKILL.md の手順6。
- **P6. 形を共通にする。** create-intent-skill とは別のスキルにする。policy.md と decisions.md の形は create-intent-skill と共通にし、どちらで作ったスキルも扱えるようにする。根拠：持ち主 2026-11-11。
- **P7. 人が決めたときは、1回の失敗でも直してよい。** そのときは、起きた回数と、決めた人と日付を decisions.md に書く。根拠：create-intent-skill/decisions.md の「5. v0 の見直し」で、1回だけ起きた2件を持ち主の判断で入れた前例。持ち主が OK（2026-11-11）。

## 非目標

- スキルを新しく作ること。それは create-intent-skill の仕事。持ち主が OK（2026-11-11）。
- 評価のループ（スキルあり・なしを並べて実行し、採点する仕組み）を組むこと。P5 の「もう一度やらせる」は、記録した失敗の場面を直したスキルで1回やり直し、同じ失敗が起きないかを見るだけで、並べて比べることも採点もしない。根拠：create-intent-skill/policy.md の非目標と、create-intent-skill/decisions.md の「5. v0 の見直し」の1行目（同じ線引き）。持ち主が OK（2026-11-11）。
- 起きていない失敗を先回りして防ぐこと。P2。持ち主が OK（2026-11-11）。
- 作業の途中でスキルを直すこと。直すのは、別のプルリクエストにする。根拠：create-intent-skill/SKILL.md の手順6。
- 参照先の文を訳したり、並べ替えたりして持ち込むこと。根拠：create-intent-skill/policy.md の非目標。

## 譲る順

方針どうしがぶつかったら、上から先に譲る。

1. 記録の形の違い（対象に policy.md と decisions.md が無い、または別の形で書かれていること）。P6 の共通の形で、対象の横に足す。ただし、SKILL.md の書き方そのものは、失敗の原因でない限り作り替えない。他人のスキルを丸ごと書き換えると、元のスキルの更新を追えなくなるため。根拠：持ち主 2026-11-11。
2. 直す速さ（1回目の失敗ですぐ直すこと）。P2 で2回を待つ。P7 で人が決めたときだけ例外。推測。
3. 指示の手厚さ（足して失敗を防ぐこと）。P3 で、削る・移す・直すを先に当てる。推測。
4. 手順の少なさ（このスキル自身の手順を短く保つこと）。推測。
5. 意図（対象のスキルの「解決したいこと」と、このスキルの解決したいこと）。最後まで譲らない。推測。

次の3つは譲る対象にしない（どの場合も守る）：起きたことだけを根拠にする、前の判断を消さない、作者の文を写さない。
