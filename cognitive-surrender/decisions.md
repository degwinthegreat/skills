# cognitive-surrender の決定の記録

cognitive-surrender を、create-intent-skill の手順で作ったときの記録（2026-11-11）。理由は [policy.md](policy.md) の項目番号（P1〜P6）で書く。要旨は、そのルールが cognitive-surrender で何を決めるかを、こちらの言葉で書いたもので、原文の訳ではない。

## 0. 要求を疑った結果（create-intent-skill の手順1の2）

既存のもので済むかを先に確かめた。retro の類は、つまずきが履歴に残ったもの（人の訂正、やり直し、失敗した道具）から学ぶ。improve-intent-skill は、起きた失敗からスキルを直す。どちらも、通ってしまって履歴に残らない候補は見ない。メモリの1行や lint は、何を見るかを決めないので代わりにならない。そこで、新しいスキルを作る。

任せた度合いの数（P3）は、モデルに写させると正しさを守れないので、数は手元の記録の道具の出力だけを使う（create-intent-skill の手順1の2の下の項目）。道具の使い方は local.md に書く。

## 3. 形（/principles の判断の手順を上から当てた結果）

1. 機械で判定できるもの：速く通したものの選び出し（返事までの時間、報告の大きさ、推奨をそのまま通した割合）は機械で判定できる。今は作らない（P6）。手元に記録の道具がある環境では、その出力を local.md の使い方で使う（P3）。選び方の誤りが同じ形で2回起きたら、スクリプトにする候補にする。
2. 分岐の条件（local.md があるか、人の答えが無いとき、記録が足りないとき、判定の3通り、渡し先の分け方）は、SKILL.md の本文に置いた。
3. 毎回要る事実は無い。常に読み込まれるメモリには何も足さない。
4. 4つの手順はどれも毎回使うので、本文に置いた。明け渡しの兆しと対策の一覧は短いので、本文に置いた。手元の道具の使い方だけを local.md に出した。local.md はこのリポジトリには入れない（`.gitignore`）。
5. 共有するもの：渡し先は名前で指す。improve-intent-skill は同じ plugin に入っている。retro はこのリポジトリに無いので、無い環境では人に渡すと書いた。
6. サブエージェント：手順3の確かめ役に使う。手動でだけ起動するスキルは事前に読み込まれないので、渡すもの（成果物、依頼、聞き方）を本文に書いた（DD1・DD2）。
7. 適用されたかは、返答で、候補ごとに選んだ理由（どの兆しか）と判定を書かせることで見える。

起動のされ方：手動でだけ（`disable-model-invocation: true`）。週に一度、人が名前で呼ぶ。定期の起動（スケジュール）にするかは、使ってから決める（P6）。

SKILL.md 自身の概念の圧縮：用語は記事の区別（任せる・明け渡す）と、policy.md の「候補」だけにした。新しい語は作っていない。

## 4. どう検証するか

4回（4週）使ったら、「明け渡していた」と判定した件数、そのうち渡し先で直った件数、人が確かめ役の指摘を誤りとして退けた回数を見て、見直す（この時期と値はエージェントの下書き）。
