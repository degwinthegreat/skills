# write-agent-rules の方針

write-agent-rules（エージェントが読むチームの規約を、差し戻せる形のチェックで書く・見直すスキル）を設計するときの方針。ルールの採否（[decisions.md](decisions.md)）は、ここの項目番号で理由を書く。

- 決めた人と日付：持ち主（2026-11-13、2026-11-14）。
  - 持ち主が決めたもの（2026-11-13）：
    - どのリポジトリでも使える汎用のスキルにすること
    - あとで種類を足せるように、対象の文書の種類を表で持つこと（P3）
    - 推す10個の原則を、差し戻せる形のチェックとして持つこと（P1）
    - 割れている論点（毎回読まれるファイルの上限、禁止形か肯定形か、理由を書くか、手本を指すか載せるか、環境が与えるものを書くか）を、スキルが決め打ちせず、使うチームに決めさせること。既定の推奨は書いてよい（P2）
    - 非目標のうち、製品の設定の手引きと、create・improve・redesign の手順の作り替え
    - 共有の方針 S1〜S3
  - 持ち主が決めたもの（2026-11-14、PR #11 の確認）：
    - 対象を規約（CLAUDE.md・AGENTS.md・steering・rules）だけに絞り、名前を write-agent-rules にすること。仕様は、別のスキル（write-spec）にする。改善のループの設計が固まってから、別の PR で作る
    - 仕様にしか当てないチェック（C3・C7）を外し、仕様の候補として decisions.md に残すこと（decisions.md の5節）
  - エージェントが下書きし、持ち主が OK したもの（2026-11-14、推奨どおり。仕様に関わる部分を除く）：
    - 解決したいことの2つの文と、P1〜P4 の言い回し
    - 例外として、C11（使ってはいけないものに代わりを並べる）をチェックに足したこと
    - 割れている論点ごとの既定の推奨（SKILL.md の T1〜T5）
    - 規約の種類に当てるチェック（SKILL.md の種類の表）
    - 人が名前で呼ぶスキルにしたこと（`disable-model-invocation: true`）
    - 非目標の残りと、譲る順
    - 検証の値と時期（decisions.md の4節）
  - 仕様を外すために言い回しを直した所（解決したいこと、非目標の1つ目）は、2026-11-14 の持ち主の決定に沿った変更。

## 解決したいこと

- エージェントが読む規約を、あるかないかで判定できるチェックで書き、見直せるようにする。差し戻す理由が、読み手の好みではなく、チェックの名前で言えるようにする。根拠：持ち主 2026-11-13（ビジョンのノートの1と3）。
- 書き方の意見が割れている論点を、スキルが決め打ちせず、使うチームに決めさせ、その決めに沿ってチェックする。根拠：持ち主 2026-11-13（ビジョンのノートの3）。

## 方針

- **P1. チェックは、あるかないかで判定できる形で書く。** 判定に読み手の判断が要る原則は、チェックにしない。根拠：持ち主 2026-11-13。
- **P2. 割れている論点は、チームに決めさせる。** スキルは既定の推奨を書き、チームの答えを、チームの規約の文書に1か所で残させる。チェックは、論点のどちら側に決めても食い違わない言い方にする。根拠：持ち主 2026-11-13。「どちら側でも食い違わない言い方」は、持ち主が OK（2026-11-14）。
- **P3. 対象の文書の種類は表で持つ。** 種類を足すときは、表に行を足し、当てるチェックを選ぶだけで済むようにする。根拠：持ち主 2026-11-13。
- **P4. どのリポジトリでも使えるようにする。** 特定の製品の設定の書き方（frontmatter の欄、ファイルを指す構文、読み込みの設定など）は書かない。根拠：持ち主 2026-11-13（入れない機能）。

## 共有の方針

このリポジトリのスキルに共通する方針は、[shared-policy.md](https://github.com/degwinthegreat/skills/blob/main/create-intent-skill/shared-policy.md) にある（S1〜S3）。この方針の上に置き、譲る順の対象にしない。write-agent-rules は1つだけでも入れられるので、cognitive-surrender と同じく、相対パスではなく GitHub の URL で指す。

## 非目標

- 仕様を扱うこと。別のスキル（write-spec）にする。根拠：持ち主 2026-11-14。
- PR の本文、README、決定の記録を扱うこと。今回の対象外で、あとで表に行を足す。根拠：持ち主 2026-11-13。
- 特定の製品（Kiro、Cursor、Claude Code など）の設定の書き方の手引き。根拠：持ち主 2026-11-13。
- create-intent-skill・improve-intent-skill・redesign-intent-workflow の手順を作り替えること。根拠：持ち主 2026-11-13。
- スキルの SKILL.md を書くこと。それは create-intent-skill と improve-intent-skill の仕事。根拠：create-intent-skill/SKILL.md の冒頭。持ち主が OK（2026-11-14）。
- 評価のループ（スキルあり・なしで並べて実行し、採点する仕組み）を組むこと。根拠：create-intent-skill/policy.md の非目標。持ち主が OK（2026-11-14）。
- 参照先の文を訳したり、並べ替えたりして持ち込むこと。根拠：create-intent-skill/policy.md の非目標。

## 譲る順

方針どうしがぶつかったら、上から先に譲る。持ち主が OK（2026-11-14）。形は create-intent-skill/policy.md の譲る順に合わせた。

1. 網羅性（参照先の原則を全部チェックにすること）
2. 参照先への忠実さ（参照先の決め方に合わせること）
3. 手順の少なさ
4. 汎用性（P4）
5. 意図（解決したいこと）。最後まで譲らない

次の2つは譲る対象にしない（どの場合も守る）：チームに決めさせる論点をスキルで決め打ちしない（P2）、作者の文を写さない。
