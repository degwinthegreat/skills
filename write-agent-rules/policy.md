## 解決したいこと

- エージェントが読む規約を、良い選択をするための薄い材料と、実例のあるルールだけで書き、見直せるようにする。根拠：持ち主 2026-11-14（足した方針）。
- 見直しで直す理由を、読み手の好みではなく、実際に起きた失敗の実例で言えるようにする。根拠：持ち主 2026-11-13（ビジョンのノートの3）、2026-11-14（残すのは実例で裏付くものだけ）。

## 方針

- **P1. 残すのは、実際の誤りの実例で裏付く失敗だけ。** 実例は、日付の付いた出来事を上流の版で読んで確かめる（S1・S2）。実例の無い原則は、もっともらしくても入れない。根拠：持ち主 2026-11-14。
- **P2. 人に聞くのは、本当に聞く必要があるものだけ。** チームの規約に決めがあれば、それに従う。決めが無く、P5 の向きでも決まらないもの（毎回読まれる規約の長さの上限の数）だけを聞く。根拠：持ち主 2026-11-13（チームに決めさせる）、2026-11-14（聞く必要が本当にあるものに絞る）。
- **P3. 対象の文書の種類は表で持つ。** 種類を足すときは、表に行を足すだけで済むようにする。根拠：持ち主 2026-11-13。
- **P4. どのリポジトリでも使えるようにする。** 特定の製品の設定の書き方（frontmatter の欄、ファイルを指す構文、読み込みの設定など）は書かない。根拠：持ち主 2026-11-13（入れない機能）。
- **P5. 薄く保つ。** スキルには、モデルが良くなっても古びない核（目的、判断の材料、避けたい失敗の実例）だけを置き、細かい手順や判定の文言は置かない。スキルが勧める規約も、同じ向きにする。規約は短くし、良い判断の材料を渡すことを主にし、ルールは実例のあるものだけにする。根拠：持ち主 2026-11-14（足した方針）。

## 非目標

- 仕様を扱うこと。別のスキル（write-spec）にする。根拠：持ち主 2026-11-14。
- PR の本文、README、決定の記録を扱うこと。今回の対象外で、あとで表に行を足す。根拠：持ち主 2026-11-13。
- 特定の製品（Kiro、Cursor、Claude Code など）の設定の書き方の手引き。根拠：持ち主 2026-11-13。
- create-intent-skill・improve-intent-skill・redesign-intent-workflow の手順を作り替えること。根拠：持ち主 2026-11-13。
- スキルの SKILL.md を書くこと。それは create-intent-skill と improve-intent-skill の仕事。根拠：create-intent-skill/SKILL.md の冒頭。持ち主が OK（2026-11-14）。
- 評価のループ（スキルあり・なしで並べて実行し、採点する仕組み）を組むこと。根拠：create-intent-skill/policy.md の非目標。持ち主が OK（2026-11-14）。
- 参照先の文を訳したり、並べ替えたりして持ち込むこと。根拠：create-intent-skill/policy.md の非目標。

## 譲る順

方針どうしがぶつかったら、上から先に譲る。持ち主が OK（2026-11-14）。形は create-intent-skill/policy.md の譲る順に合わせた。

1. 網羅性（参照先の原則を全部入れること）
2. 参照先への忠実さ（参照先の決め方に合わせること）
3. 手順の少なさ
4. 汎用性（P4）
5. 意図（解決したいこと）。最後まで譲らない

次の2つは譲る対象にしない（どの場合も守る）：チームの規約にある決めを、スキルの向きで上書きしない（P2）、作者の文を写さない。
